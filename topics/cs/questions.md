## 프로세스와 스레드의 차이를 설명해주세요.

**난이도**: 기초

**핵심 키워드**: 자원 할당 단위, 스케줄링 단위, Stack 독립, Heap 공유, IPC, 장애 격리, 동기화

**모범 답변 (말하기 형태)**:

> 프로세스는 운영체제로부터 자원을 할당받는 실행 단위이고, 스레드는 프로세스 안에서 실제로 CPU를 할당받아 실행되는 흐름입니다. 가장 큰 차이는 메모리 구조입니다. 프로세스는 Code, Data, Heap, Stack 영역을 각자 독립적으로 가지기 때문에 서로의 메모리에 직접 접근할 수 없고, 통신하려면 파이프나 소켓 같은 IPC를 거쳐야 합니다. 반면 스레드는 Stack만 따로 가지고 Code, Data, Heap은 같은 프로세스의 다른 스레드와 공유합니다. 그래서 스레드는 생성 비용과 컨텍스트 스위칭 비용이 작고 데이터를 주고받기 쉽다는 장점이 있습니다. 하지만 공유 자원에 여러 스레드가 동시에 접근하면 실행 순서에 따라 결과가 달라지는 경쟁 상태가 생기기 때문에 락이나 원자적 연산 같은 동기화가 필요합니다. 또 장애 격리 측면에서도 차이가 있는데, 프로세스는 하나가 죽어도 다른 프로세스에 영향을 주지 않지만 스레드는 한 스레드의 치명적인 오류가 프로세스 전체를 종료시킬 수 있습니다. Spring 애플리케이션으로 보면 서버 하나가 JVM 프로세스 하나이고, 요청마다 Tomcat 스레드 풀의 스레드가 처리하면서 싱글톤 빈을 공유하기 때문에 빈에 상태를 두지 않는 것이 중요합니다.

## 컨텍스트 스위칭이란 무엇이고, 스레드를 무한정 늘리면 안 되는 이유는 무엇인가요?

**난이도**: 기초

**핵심 키워드**: PCB/TCB, 레지스터 저장·복원, 주소 공간 교체, TLB 플러시, 오버헤드, CPU bound vs I/O bound

**경험 연결 힌트**: 부하 테스트로 스레드 수를 조정하고 CPU가 먼저 포화되는 것을 확인한 경험

**모범 답변 (말하기 형태)**:

> 컨텍스트 스위칭은 CPU가 실행 중인 작업의 상태, 즉 레지스터 값과 프로그램 카운터, 스택 포인터를 PCB나 TCB에 저장하고, 다음에 실행할 작업의 상태를 복원하는 과정입니다. 이 덕분에 코어 수보다 많은 작업이 동시에 실행되는 것처럼 보입니다. 프로세스 간 전환은 주소 공간 자체가 바뀌기 때문에 페이지 테이블을 교체하고 TLB가 비워져서, 전환 직후 주소 변환 캐시 미스가 늘어나 비용이 큽니다. 같은 프로세스의 스레드끼리는 주소 공간을 공유하므로 레지스터와 스택만 바꾸면 되어 상대적으로 가볍습니다. 하지만 가볍다고 해도 전환하는 동안 CPU는 실제 비즈니스 로직을 전혀 처리하지 못하고, CPU 캐시도 식습니다. 그래서 스레드를 무한정 늘리면 처리량이 늘기는커녕 전환 비용과 스레드별 스택 메모리 때문에 오히려 성능이 떨어집니다. 적정 스레드 수는 작업 성격에 따라 다른데, CPU 연산 위주라면 코어 수 근처가 적당하고, DB나 외부 API를 기다리는 시간이 긴 I/O 위주라면 대기 비율만큼 더 늘릴 수 있습니다. 다만 공식은 출발점일 뿐이고, 실제로는 부하 테스트에서 스레드 수를 바꿔 가며 처리량, 지연 시간, CPU 사용률을 같이 보고 병목이 스레드인지 CPU인지 확인한 뒤 결정하는 것이 맞다고 생각합니다.

**꼬리 질문 예시**:

- 스레드 1개가 차지하는 메모리는 대략 어느 정도이고 어디에 쓰이나요?
- I/O 대기가 긴 서비스에서 스레드를 늘리는 대신 쓸 수 있는 방법은?

## 데드락의 발생 조건과 해결 방법을 설명해주세요.

**난이도**: 기초

**핵심 키워드**: 상호 배제, 점유 대기, 비선점, 순환 대기, 락 획득 순서, tryLock 타임아웃, 탐지 후 회복

**모범 답변 (말하기 형태)**:

> 데드락은 둘 이상의 작업이 서로 상대가 가진 자원을 기다리면서 영원히 진행하지 못하는 상태입니다. 데드락은 네 가지 조건이 동시에 성립할 때 발생합니다. 자원을 한 번에 하나만 쓸 수 있는 상호 배제, 자원을 가진 채로 다른 자원을 기다리는 점유 대기, 다른 작업이 가진 자원을 강제로 뺏을 수 없는 비선점, 그리고 대기 관계가 원형으로 이어지는 순환 대기입니다. 반대로 말하면 이 중 하나만 깨도 데드락은 발생하지 않습니다. 실무에서 가장 많이 쓰는 방법은 순환 대기를 깨는 것으로, 여러 자원을 잠가야 할 때 항상 같은 순서로 획득하도록 규칙을 정합니다. 예를 들어 계좌 이체에서 두 계좌를 잠글 때 계좌 ID가 작은 쪽부터 잠그면 A에서 B, B에서 A로의 동시 이체가 서로를 막지 않습니다. 비선점을 깨는 방법으로는 Java의 tryLock에 타임아웃을 주어 일정 시간 안에 못 얻으면 가진 락을 풀고 재시도하게 할 수 있습니다. 데이터베이스는 조건을 미리 막기보다 탐지 후 회복 전략을 쓰는데, InnoDB는 대기 그래프에서 순환을 찾으면 한쪽 트랜잭션을 롤백시킵니다. 그래서 애플리케이션은 데드락 예외를 받았을 때 재시도할 수 있게 설계하고, 트랜잭션을 짧게 유지하는 것이 중요합니다.

**꼬리 질문 예시**:
- 데드락과 기아(starvation)의 차이는?
- 분산 락 환경에서는 데드락을 어떻게 방지하나요? (TTL)
- DB 데드락이 났을 때 원인을 어떻게 찾나요? → [[topics/mysql/questions#Deadlock 감지·방지]]

## Mutex와 Semaphore의 차이를 설명해주세요.

**난이도**: 기초

**핵심 키워드**: 임계 영역, 동시 진입 수, 소유권, 카운팅 세마포어, synchronized(모니터), ReentrantLock

**모범 답변 (말하기 형태)**:

> Mutex와 Semaphore는 모두 여러 스레드가 공유 자원에 접근할 때 동시성을 제어하는 도구인데, 동시에 들어갈 수 있는 수와 소유권에서 차이가 납니다. Mutex는 임계 영역에 오직 하나의 스레드만 들어가게 하는 잠금이고, 락을 획득한 스레드만 해제할 수 있다는 소유권 개념이 있습니다. 그래서 공유 데이터의 일관성을 지키는 상호 배제 용도로 씁니다. Semaphore는 내부에 카운터를 두고 정해진 개수만큼 동시 진입을 허용합니다. 진입할 때 카운터를 줄이고 나갈 때 늘리며, 0이면 대기합니다. 소유권이 없어서 획득한 스레드가 아닌 다른 스레드가 반납할 수도 있습니다. 그래서 커넥션 풀처럼 한정된 자원 N개의 동시 사용량을 제한하거나, 외부 API 호출을 동시에 몇 개까지만 보내도록 제어할 때 적합합니다. 카운터가 1인 이진 세마포어는 Mutex와 비슷해 보이지만 소유권이 없다는 점에서 다릅니다. Java에서는 synchronized가 모니터 방식으로 상호 배제와 wait, notify 조건 대기를 함께 제공하고, 더 세밀한 제어가 필요하면 타임아웃과 인터럽트를 지원하는 ReentrantLock을, 동시 접근 수 제한에는 java.util.concurrent.Semaphore를 사용합니다. 다만 이런 락은 모두 JVM 하나 안에서만 유효하기 때문에 서버가 여러 대라면 Redis나 DB 기반의 분산 락이 필요합니다.

## HashMap의 동작 원리와 해시 충돌 처리 방식을 설명해주세요.

**난이도**: 기초

**핵심 키워드**: hashCode, 버킷 인덱스, 체이닝, 개방 주소법, 트리화(8개), 부하율 0.75, 리사이징, equals/hashCode 계약

**모범 답변 (말하기 형태)**:

> HashMap은 키의 hashCode를 기반으로 버킷 배열의 인덱스를 계산해 값을 저장하기 때문에 평균적으로 조회와 삽입이 O(1)입니다. Java의 HashMap은 hashCode의 상위 비트를 하위 비트와 섞은 뒤 배열 크기로 나눈 위치를 버킷으로 사용합니다. 서로 다른 키가 같은 버킷에 들어가는 것을 해시 충돌이라고 하는데, 해결 방식은 크게 두 가지입니다. 같은 버킷에 연결 리스트로 이어 붙이는 체이닝과, 충돌하면 다른 빈 칸을 찾아가는 개방 주소법입니다. Java HashMap은 체이닝을 사용하고, 한 버킷의 노드가 8개 이상이 되면서 전체 테이블 크기가 64 이상이면 레드블랙 트리로 바꿔 최악의 경우도 O(log n)으로 막습니다. 또 저장된 개수가 용량의 75퍼센트를 넘으면 배열을 두 배로 늘리고 모든 엔트리를 다시 배치하는 리사이징이 일어나는데, 비용이 크기 때문에 들어갈 개수를 미리 알면 초기 용량을 지정하는 것이 좋습니다. 실무에서 주의할 점은 키로 쓰는 객체가 equals를 재정의했다면 hashCode도 반드시 함께 재정의해야 한다는 것입니다. 그렇지 않으면 논리적으로 같은 키가 다른 버킷에 들어가 조회가 실패합니다. 그리고 HashMap은 스레드 안전하지 않기 때문에 여러 스레드가 동시에 쓰는 환경에서는 ConcurrentHashMap을 사용해야 합니다.

## TCP와 UDP의 차이, 그리고 3-way handshake를 설명해주세요.

**난이도**: 기초

**핵심 키워드**: 연결 지향, 신뢰성, 순서 보장, 재전송, 흐름·혼잡 제어, SYN/SYN-ACK/ACK, 4-way handshake, TIME_WAIT

**모범 답변 (말하기 형태)**:

> TCP는 연결 지향 프로토콜로, 데이터를 보내기 전에 연결을 수립하고 순서 보장, 유실 시 재전송, 흐름 제어와 혼잡 제어를 통해 신뢰성 있는 전송을 보장합니다. UDP는 연결 수립 없이 데이터그램을 바로 보내기 때문에 헤더가 작고 빠르지만, 순서나 도착을 보장하지 않습니다. 그래서 HTTP 요청이나 DB 연결처럼 데이터가 정확해야 하는 곳에는 TCP를, DNS 조회나 실시간 영상·음성처럼 약간의 손실보다 지연이 더 치명적인 곳에는 UDP를 씁니다. HTTP/3는 UDP 위에 QUIC을 올려 신뢰성을 애플리케이션 계층에서 구현하기도 합니다. TCP 연결 수립은 3-way handshake로 이루어집니다. 클라이언트가 SYN을 보내고, 서버가 SYN과 ACK를 함께 응답하고, 클라이언트가 ACK를 보내면 연결이 수립됩니다. 세 번 주고받는 이유는 양쪽이 서로의 송신과 수신이 모두 가능한지, 그리고 시퀀스 번호 초기값을 확인하기 위해서입니다. 종료는 4-way handshake로 FIN과 ACK를 양방향으로 주고받고, 먼저 종료한 쪽은 늦게 도착하는 패킷과 마지막 ACK 유실에 대비해 TIME_WAIT 상태로 잠시 대기합니다. 짧은 연결을 대량으로 맺고 끊으면 TIME_WAIT가 쌓여 포트가 부족해질 수 있어서, 실무에서는 커넥션 풀과 Keep-Alive로 연결을 재사용합니다.

## 브라우저 주소창에 URL을 입력하면 어떤 일이 일어나나요?

**난이도**: 기초

**핵심 키워드**: DNS 조회, TCP 연결, TLS 핸드셰이크, HTTP 요청, 리버스 프록시, 로드밸런서, 애플리케이션 서버, 렌더링

**모범 답변 (말하기 형태)**:

> 먼저 브라우저는 도메인의 IP 주소를 알아내기 위해 DNS 조회를 합니다. 브라우저 캐시, 운영체제 캐시와 hosts 파일을 확인하고, 없으면 리졸버가 루트 네임서버, TLD 네임서버, 도메인의 권한 네임서버 순서로 질의해 IP를 받아옵니다. IP를 알게 되면 해당 서버의 443 포트로 TCP 3-way handshake를 해서 연결을 맺고, HTTPS이므로 TLS 핸드셰이크로 인증서를 검증하고 대칭 세션 키를 합의합니다. 그다음 암호화된 채널로 HTTP 요청을 보냅니다. 서버 쪽에서는 보통 로드밸런서나 Nginx 같은 리버스 프록시가 요청을 받아 TLS를 종료하고, 경로에 따라 API Gateway나 Spring 애플리케이션으로 전달합니다. 애플리케이션에서는 Tomcat 스레드가 요청을 받아 필터와 DispatcherServlet을 거쳐 컨트롤러, 서비스, 리포지토리를 실행하고, 필요하면 Redis 캐시를 먼저 보거나 DB에 쿼리한 뒤 JSON 응답을 만듭니다. 응답이 돌아오면 브라우저는 HTML을 파싱해 DOM을 만들고 CSS와 합쳐 렌더링하며, 추가로 필요한 JS와 이미지 리소스를 다시 요청합니다. 백엔드 관점에서는 이 경로의 각 구간, 즉 DNS, 연결 수립, 프록시, 애플리케이션 처리, DB, 응답 전송 중 어디서 지연이 생기는지를 나눠 보는 것이 성능 문제를 진단하는 출발점이라고 생각합니다.

## HTTP와 HTTPS의 차이를 설명해주세요.

**난이도**: 기초

**핵심 키워드**: TLS, 암호화, 443포트, 기밀성, 무결성, 인증

**모범 답변 방향**:

HTTP는 데이터를 평문으로 전송하기 때문에 네트워크 경로상에서 누군가 패킷을 가로채면 내용을 그대로 읽을 수 있고, 위변조도 가능합니다. HTTPS는 이 HTTP 위에 TLS 암호화 레이어를 추가한 프로토콜로, 기본 포트는 443을 사용합니다. HTTPS가 보장하는 것은 크게 세 가지입니다. 첫째는 기밀성으로, 데이터를 암호화해 제3자가 내용을 볼 수 없게 합니다. 둘째는 무결성으로, 전송 중 데이터가 변조됐는지 MAC을 통해 감지할 수 있습니다. 셋째는 인증으로, 서버 인증서를 통해 내가 접속하는 서버가 신뢰할 수 있는 서버인지 확인합니다. 실제 통신 시에는 TLS 핸드셰이크 과정에서 세션 키를 교환한 뒤, 이후 본문 통신은 빠른 대칭 암호화로 처리합니다. 공개키 암호화를 계속 쓰면 연산 비용이 크기 때문에, 키 교환에만 공개키를 쓰고 본문에는 대칭키를 사용하는 구조입니다.

## TLS Handshake 과정을 단계별로 설명해주세요.

**난이도**: 중급

**핵심 키워드**: Client Hello, Server Hello, 인증서, Pre-Master Secret, Session Key, 대칭키

**모범 답변 방향**:

TLS 핸드셰이크는 클라이언트와 서버가 암호화 통신을 시작하기 전에 세션 키를 안전하게 교환하는 과정입니다. 먼저 클라이언트가 Client Hello를 보내는데, 자신이 지원하는 암호화 방식 목록과 클라이언트 랜덤값을 함께 전송합니다. 서버는 Server Hello로 응답하면서 암호화 방식을 선택하고, 서버 랜덤값과 서버 인증서를 클라이언트에게 전달합니다. 클라이언트는 이 인증서를 OS나 브라우저에 사전 설치된 CA 루트 인증서로 검증한 뒤, 인증서에 포함된 서버의 공개키로 Pre-Master Secret을 암호화해 서버에 전송합니다. 이 단계까지 공개키 암호화가 쓰이는 이유는 Pre-Master Secret을 서버 외에는 아무도 복호화하지 못하게 하기 위함입니다. 이후 양측은 클라이언트 랜덤, 서버 랜덤, Pre-Master Secret 세 값을 조합해 동일한 세션 키를 각자 독립적으로 도출하고, 이때부터는 이 대칭 세션 키로 빠르게 통신합니다. 공개키 암호화는 연산 비용이 높기 때문에 키 교환 단계에만 사용하고, 실제 데이터 전송은 대칭키로 처리하는 것이 핵심 설계 원칙입니다.

**꼬리 질문 예시**:
- "왜 공개키로 계속 통신하지 않고 대칭키로 전환하나요?"
- "TLS 1.2와 TLS 1.3의 차이는 무엇인가요?"
- "인증서는 어떻게 신뢰하나요? CA 체인이란?"

**자주 나오는 오답 패턴** (2026-04-01 세션):
- ❌ "클라이언트가 인증서와 공개키를 서버에게 보낸다" → ✅ 서버가 클라이언트에게 전송
- ❌ "서버가 대칭키로 검증한다" → ✅ 대칭키(세션 키)는 Handshake 마지막에 도출. 키 교환 단계에서는 클라이언트가 서버의 공개키로 암호화
- ❌ "클라이언트가 인증서를 인증 회사에서 직접 다운로드" → ✅ 서버가 Handshake 중 인증서를 전송. 클라이언트는 OS/브라우저에 사전 설치된 CA 루트 인증서로 신뢰 여부 검증

## HTTP 프로토콜 버전과 HOL Blocking

**난이도**: 기초

**핵심 키워드**: HOL Blocking, HTTP/1.1 Pipelining, HTTP/2 Multiplexing, Stream, 인터리브, TCP 레벨 HOL Blocking, QUIC, UDP, 0-RTT, Connection Migration

**HTTP/1.1 — HOL Blocking**:
- 하나의 TCP 연결에서 요청을 **순서대로(serial)** 처리 → 앞 요청 응답이 느리면 뒤 요청이 전부 대기
- Pipelining 지원하지만 응답은 반드시 요청 순서 그대로여야 함 → 사실상 HOL Blocking 해결 안 됨
- 브라우저 우회: 도메인당 TCP 연결 6개 병렬 오픈 → 연결 비용 증가
- **주의**: 스레드 할당 문제가 아닌 **TCP 연결 내 프로토콜 순서 문제**

**HTTP/2 — Application 레벨 HOL Blocking 해결**:
- 하나의 TCP 연결에서 여러 **Stream** 병렬 처리
- 각 Stream은 독립적인 요청/응답 쌍 → 메시지를 **프레임 단위로 쪼개 인터리브(interleave) 전송**
- 콜백 방식이 아님 — 프레임 수준의 멀티플렉싱

**HTTP/2의 남은 한계 — TCP 레벨 HOL Blocking**:
- TCP 패킷이 하나 유실 → OS가 재전송을 기다리는 동안 해당 TCP 연결 위 **모든 Stream이 함께 멈춤**
- Stream이 10개여도 하나의 TCP 패킷 손실에 전부 대기

**HTTP/3 (QUIC) — TCP 레벨 HOL Blocking 해결**:
- **UDP 기반 QUIC** 프로토콜 사용
- 각 Stream이 독립적인 흐름 → 하나의 Stream 패킷 유실이 다른 Stream에 영향 없음
- **0-RTT/1-RTT 연결**: TCP 3-way handshake + TLS를 합산해 연결 수립 시간 단축
- **Connection Migration**: IP 변경(Wi-Fi → 4G)에도 Connection ID 기반으로 연결 유지

**성능 요약**:
| | Application HOL | TCP HOL | 연결 비용 |
|---|---|---|---|
| HTTP/1.1 | ❌ 있음 | ❌ 있음 | 도메인당 6 TCP 연결 |
| HTTP/2 | ✅ 해결 | ❌ 여전함 | 1 TCP 연결 |
| HTTP/3 | ✅ 해결 | ✅ 해결 | 1 QUIC 연결 + 0-RTT |

## TLS 1.2와 TLS 1.3의 차이점은 무엇인가요?

**난이도**: 중급

**핵심 키워드**: RTT, 0-RTT, Perfect Forward Secrecy, Cipher Suite, 성능

**모범 답변 방향**:

TLS 1.2와 1.3의 가장 큰 차이는 핸드셰이크 성능과 보안 강화입니다. TLS 1.2는 핸드셰이크에 2 RTT가 필요하고 RSA 키 교환을 지원하는데, RSA는 서버의 개인키가 노출되면 과거 통신 내용까지 복호화할 수 있다는 문제가 있습니다. TLS 1.3은 핸드셰이크를 1 RTT로 줄여 연결 수립 속도를 높이고, RSA 키 교환을 제거해 Perfect Forward Secrecy를 기본으로 적용합니다. PFS는 세션마다 임시 키를 생성하기 때문에 특정 세션의 키가 유출되더라도 다른 세션의 통신 내용은 안전하게 보호됩니다. 또한 TLS 1.3은 세션 재개 시 0-RTT를 지원해, 이전에 연결한 서버와 다시 통신할 때 핸드셰이크 없이 바로 데이터를 전송할 수 있습니다. 다만 0-RTT는 재전송 공격(Replay Attack)에 취약하다는 보안 트레이드오프가 있어, 멱등성이 보장되는 요청에만 적용하는 것이 권장됩니다. 취약한 Cipher Suite도 정리돼 보안 수준 자체가 높아졌고, 2025년 기준으로 TLS 1.3이 권장 버전이며 TLS 1.1 이하는 사용이 금지된 수준입니다.

- "0-RTT의 보안 위험성은?"

## HTTPS를 사용해도 보안 위협이 있을 수 있나요?

**난이도**: 심화

**핵심 키워드**: MITM, 인증서 위조, 만료 인증서, HSTS, 혼합 콘텐츠

**모범 답변 방향**:

HTTPS는 전송 구간을 암호화하는 것이지 모든 보안 문제를 해결하는 것은 아닙니다. 서버나 클라이언트 자체의 취약점, 애플리케이션 레벨 취약점은 HTTPS와 무관하게 존재합니다. 구체적인 위협을 말씀드리면, 먼저 인증서 관련 문제가 있습니다. 인증서가 만료됐거나 도메인이 불일치하거나 신뢰할 수 없는 CA에서 발급된 경우 브라우저가 경고를 띄우는데, 사용자가 이 경고를 무시하고 진행하면 MITM 공격이 가능해집니다. 다음으로 혼합 콘텐츠 문제가 있습니다. HTTPS 페이지 안에서 HTTP로 이미지나 스크립트를 불러오면, 그 리소스는 암호화되지 않아 공격자가 중간에서 변조할 수 있습니다. 또한 HSTS가 설정되지 않은 경우, 사용자가 처음 HTTP로 접속하는 순간을 공격자가 낚아채 HTTPS 업그레이드 응답을 가로채는 다운그레이드 공격이 가능합니다. HSTS는 브라우저에 "이 도메인은 항상 HTTPS로만 접속하라"고 미리 지시해 이 문제를 방지합니다. 실무에서는 HSTS 설정, 인증서 자동 갱신, HTTP 요청의 HTTPS 강제 리다이렉트를 기본으로 적용하는 것이 중요합니다.

- "인증서 유효기간이 왜 점점 짧아지는 추세인가요?"

## Nginx와 Tomcat의 차이를 설명해주세요.

**난이도**: 기초

**핵심 키워드**: 웹 서버, WAS, Event-driven, Thread-per-request, 정적 파일, 리버스 프록시

**모범 답변 방향**:

Nginx와 Tomcat은 역할 자체가 다른 서버입니다. Nginx는 웹 서버로, 정적 파일 서빙, 리버스 프록시, 로드 밸런싱이 주된 역할입니다. Tomcat은 WAS, 즉 웹 애플리케이션 서버로, 서블릿 컨테이너 역할을 하며 Java 기반의 동적 요청을 처리합니다. 실무에서는 Nginx를 앞단에 두고 Tomcat을 뒷단에 두는 구조를 많이 사용합니다. Nginx가 외부 요청을 받아 TLS 종료까지 처리한 다음 평문 HTTP로 Tomcat에 넘기면, Tomcat은 TLS 처리 부하 없이 비즈니스 로직에만 집중할 수 있습니다. Nginx를 Tomcat 앞에 두는 또 다른 이유는 보안과 성능 측면에서도 있습니다. Tomcat을 외부에 직접 노출하지 않으면 공격 표면을 줄일 수 있고, 정적 파일은 Nginx가 훨씬 빠르게 처리할 수 있기 때문에 Tomcat의 스레드 자원을 동적 요청에만 집중시킬 수 있습니다. 요청 처리 모델도 근본적으로 다른데, Nginx는 이벤트 기반 Non-blocking I/O 방식이고 Tomcat은 기본적으로 요청당 스레드를 할당하는 방식이라 대규모 동시 연결 처리에서 Nginx가 훨씬 유리합니다.

## Nginx + Tomcat 조합의 non-blocking 이점

### Q. Spring Boot(Tomcat) 앞에 Nginx를 두면 non-blocking 관점에서 어떤 이점이 있는지 설명해주세요. Tomcat의 thread-per-request 모델에서 "Slow Client Problem"이 왜 발생하는지, Nginx가 이를 어떻게 해결하는지 포함해서 설명해주세요.

**난이도:** 중급

**핵심 키워드:** thread-per-request, event-driven non-blocking, Slow Client Problem, 응답 버퍼링, 네트워크 I/O 분리

**모범 답변 방향:**

Tomcat은 요청당 스레드 1개를 점유하는 thread-per-request 모델입니다. 문제는 응답을 클라이언트에 전송하는 동안에도 스레드가 묶인다는 것입니다. 서버가 응답을 만드는 시간은 수 ms이지만, 클라이언트 네트워크가 느리면 전송 완료까지 수백 ms~수초가 걸립니다. 이 대기 시간 동안 Tomcat 스레드가 아무것도 못 하고 점유된 채 기다립니다. 동시 접속이 많으면 스레드 풀이 고갈되어 새 요청을 처리할 수 없게 됩니다. 이것이 Slow Client Problem입니다. Nginx는 event-driven 구조로 소수의 워커 스레드로 수천 개의 연결을 non-blocking으로 처리합니다. Tomcat 앞에 Nginx를 두면 흐름이 달라집니다. Tomcat이 응답을 생성해 Nginx에게 전달하는 건 같은 서버 내부 통신이라 거의 즉각적입니다. Tomcat은 Nginx에게 응답을 넘기는 즉시 스레드를 반환합니다. 이후 느린 클라이언트에게 데이터를 천천히 전송하는 네트워크 I/O 대기는 Nginx가 non-blocking으로 담당합니다. 결과적으로 Tomcat 스레드가 묶이는 시간이 "비즈니스 로직 처리 시간"으로만 한정됩니다. 추가 이점으로 Keep-Alive 유휴 연결 관리와 정적 파일(image, css, js) 처리도 Nginx가 담당해 Tomcat 부하를 더 줄일 수 있습니다.

## Nginx가 동시 연결을 효율적으로 처리하는 원리는 무엇인가요?

**난이도**: 중급

**핵심 키워드**: Event-driven, Non-blocking I/O, epoll, Master-Worker, C10K, Context Switching

**모범 답변 방향**:

Nginx가 동시 연결을 효율적으로 처리하는 핵심은 이벤트 기반 Non-blocking I/O 구조입니다. Tomcat 같은 Thread-per-request 방식은 요청마다 스레드를 할당하기 때문에, I/O 대기 중에도 스레드가 자원을 점유하고 있습니다. 동시 연결이 수천 개를 넘어가면 스레드 수가 폭발적으로 늘어나고, 이들 사이의 Context Switching 오버헤드가 심각해집니다. Nginx는 Master-Worker 구조로 동작하는데, Master 프로세스는 설정 관리와 Worker 관리를 담당하고, 실제 요청 처리는 Worker 프로세스가 담당합니다. Worker 하나가 epoll을 통해 수천 개 이상의 커넥션을 동시에 감시하면서, I/O가 준비된 소켓에만 반응하는 방식입니다. I/O 대기 중에는 그 커넥션을 블록하지 않고 다른 커넥션의 이벤트를 처리하러 넘어가기 때문에, 스레드를 새로 생성하지 않고도 수많은 연결을 처리할 수 있습니다. 이 구조가 C10K 문제, 즉 서버 하나에서 10,000개 동시 연결을 처리하는 것을 목표로 설계된 아키텍처입니다. Worker 프로세스 수는 보통 CPU 코어 수와 동일하게 설정해, 코어 간 Context Switching 없이 각 Worker가 한 코어를 전담하도록 구성합니다.

## Nginx의 sendfile이란 무엇이고, 왜 정적 파일 전송에 유리한가요?

**난이도**: 중급

**핵심 키워드**: sendfile, Zero-copy, 커널 버퍼, 유저 스페이스, tcp_nopush

**모범 답변 방향**:

sendfile은 정적 파일을 전송할 때 불필요한 데이터 복사를 제거하는 커널 수준의 최적화 기능입니다. 일반적인 파일 전송 흐름을 보면, 디스크에서 데이터를 읽어 커널 버퍼에 올리고, 이것을 다시 유저 스페이스로 복사한 뒤, 애플리케이션이 소켓 버퍼로 다시 복사해 전송합니다. 이 과정에서 데이터가 최소 두세 번 복사되고, 유저 스페이스와 커널 스페이스 사이를 오가는 컨텍스트 전환도 발생합니다. sendfile 시스템 콜을 사용하면 커널 버퍼에서 소켓 버퍼로 데이터를 직접 전달할 수 있어, 유저 스페이스를 거치지 않는 Zero-copy 전송이 가능합니다. CPU와 메모리 오버헤드가 크게 줄어들기 때문에 이미지, CSS, JS 같은 대용량 정적 파일을 대량으로 서빙하는 환경에서 효율이 극대화됩니다. Nginx 설정에서 `sendfile on`과 `tcp_nopush on`을 함께 쓰면 패킷을 최대한 모아서 보내는 추가 최적화도 됩니다. 다만 sendfile은 디스크에서 직접 읽는 정적 파일에만 적용되고, 프록시를 통해 받아온 동적 콘텐츠에는 적용할 수 없다는 한계가 있습니다. 또한 NFS 같은 네트워크 파일시스템 환경에서는 커널이 sendfile을 지원하지 않는 경우가 있어 주의가 필요합니다.

## 가상 메모리와 페이지 폴트를 설명하고, 컨테이너에서 JVM이 메모리 한도로 강제 종료되는 이유를 설명해주세요.

**난이도**: 중급

**핵심 키워드**: 가상 주소 공간, 페이지 테이블, TLB, 페이지 폴트, 스래싱, RSS, cgroup, OOM Killer, 비힙 메모리

**경험 연결 힌트**: 컨테이너 메모리 한도 초과로 서비스가 재시작된 원인을 비힙 메모리로 분석한 경험

**모범 답변 (말하기 형태)**:

> 가상 메모리는 각 프로세스에게 독립된 연속 주소 공간이 있는 것처럼 보이게 하고, 실제 물리 메모리 위치는 운영체제가 페이지 테이블로 매핑하는 기법입니다. 메모리를 고정 크기 페이지로 나누기 때문에 외부 단편화가 없고, 프로세스 간 메모리가 격리되며, 물리 메모리보다 큰 공간을 쓸 수 있습니다. 주소 변환은 매번 페이지 테이블을 보면 느리기 때문에 TLB라는 하드웨어 캐시가 최근 변환 결과를 저장합니다. 프로세스가 접근한 페이지가 물리 메모리에 없으면 페이지 폴트가 발생하고, 운영체제가 디스크에서 페이지를 올린 뒤 실행을 재개합니다. 이런 폴트가 과도하면 CPU가 페이지 교체만 하는 스래싱이 일어납니다. 컨테이너 환경에서 중요한 점은 메모리 한도가 cgroup으로 실제 사용 중인 물리 메모리, 즉 RSS를 기준으로 걸린다는 것입니다. 한도를 넘으면 JVM이 OutOfMemoryError를 던지는 게 아니라 커널의 OOM Killer가 프로세스를 바로 종료시켜 exit code 137로 재시작됩니다. JVM의 RSS는 힙만이 아니라 Metaspace, JIT 코드 캐시, Direct Memory, 그리고 스레드 수만큼의 스레드 스택까지 포함합니다. 그래서 Xmx를 컨테이너 한도에 딱 맞추면 비힙 영역 때문에 한도를 넘을 수 있고, 비힙 영역의 상한과 스레드 수까지 합산해서 여유를 두고 설정해야 합니다.

## Blocking I/O와 I/O 멀티플렉싱(epoll)의 차이, 그리고 이것이 WebFlux·Nginx와 어떤 관계인지 설명해주세요.

**난이도**: 중급

**핵심 키워드**: thread-per-request, non-blocking, select/poll/epoll, 준비 이벤트, 이벤트 루프, Netty, 블로킹 호출 금지

**경험 연결 힌트**: Spring Cloud Gateway(WebFlux)에서 WebClient 논블로킹 호출을 구현한 경험

**모범 답변 (말하기 형태)**:

> Blocking I/O는 소켓에서 데이터를 읽을 때 데이터가 올 때까지 호출한 스레드가 멈춰서 기다리는 방식입니다. 그래서 Tomcat 같은 thread-per-request 모델은 연결이나 요청 하나당 스레드 하나를 쓰고, 외부 호출이 느려지면 스레드가 대기 상태로 묶여 풀이 고갈될 수 있습니다. I/O 멀티플렉싱은 하나의 스레드가 여러 소켓을 등록해 두고, 읽거나 쓸 준비가 된 소켓만 운영체제에게 통지받아 처리하는 방식입니다. 초기의 select와 poll은 호출할 때마다 감시할 파일 디스크립터 목록 전체를 커널에 넘기고 전체를 순회해야 해서 연결 수가 늘면 비용이 선형으로 증가했습니다. 리눅스의 epoll은 감시 대상을 커널에 한 번 등록하고, 준비된 디스크립터만 돌려주기 때문에 수만 개의 연결도 적은 스레드로 처리할 수 있습니다. Nginx가 워커 프로세스 몇 개로 대량의 동시 연결을 처리하는 것, 그리고 Spring WebFlux와 Spring Cloud Gateway가 사용하는 Netty가 코어 수 정도의 이벤트 루프 스레드로 동작하는 것이 모두 이 원리입니다. 대신 이벤트 루프 스레드에서 JDBC 같은 블로킹 호출을 하면 그 스레드가 담당하는 모든 연결이 멈추기 때문에, 블로킹 작업은 별도 스레드 풀로 분리하거나 논블로킹 클라이언트를 사용해야 합니다.

## DB 인덱스에 B+Tree를 사용하는 이유를 해시·이진 트리와 비교해 설명해주세요.

**난이도**: 중급

**핵심 키워드**: 디스크 I/O, 페이지, 높은 팬아웃, 낮은 트리 높이, 리프 연결 리스트, 범위 조회, 해시 인덱스 한계, 클러스터드 인덱스

**경험 연결 힌트**: EXPLAIN으로 테이블 접근을 확인하고 커버링 인덱스를 적용한 경험

**모범 답변 (말하기 형태)**:

> 데이터베이스 인덱스는 디스크나 페이지 단위로 읽히기 때문에, 한 번 조회할 때 읽는 페이지 수, 즉 디스크 I/O 횟수를 줄이는 것이 핵심입니다. 이진 탐색 트리는 노드 하나에 키가 하나라서 데이터가 많아지면 트리 높이가 깊어지고, 높이만큼 페이지를 읽어야 합니다. B+Tree는 노드 하나를 하나의 페이지로 두고 그 안에 수백 개의 키를 넣기 때문에 팬아웃이 매우 커서, 수천만 건이 있어도 트리 높이가 3에서 4 정도로 유지됩니다. 또 B-Tree와 달리 B+Tree는 실제 데이터나 PK를 리프 노드에만 두고 내부 노드에는 키만 저장해 한 페이지에 더 많은 키를 담을 수 있고, 리프 노드끼리 연결 리스트로 이어져 있어서 범위 조회나 정렬된 순서로 읽을 때 리프를 옆으로 따라가기만 하면 됩니다. 해시 인덱스는 등치 조회는 O(1)로 빠르지만 순서가 없어서 범위 조건, 정렬, 그리고 복합 인덱스의 앞부분 컬럼만 쓰는 조회를 지원하지 못합니다. 그래서 범용 RDB의 기본 인덱스는 B+Tree입니다. InnoDB에서는 PK 인덱스의 리프에 행 전체가 저장되는 클러스터드 인덱스 구조이고, 세컨더리 인덱스 리프에는 PK 값이 저장됩니다. 그래서 필요한 컬럼이 모두 세컨더리 인덱스에 있으면 PK로 다시 찾아가지 않는 커버링 인덱스가 되어 조회가 크게 빨라집니다.

**경험 연결 힌트**: Snowflake ID 정밀도 손실로 발생한 조회 오류를 추적한 경험

**모범 답변 (말하기 형태)**:

> 원인은 JavaScript의 Number 타입이 정수와 실수를 구분하지 않고 모두 IEEE 754 64비트 부동소수점으로 표현하기 때문입니다. 64비트 중 가수부가 53비트라서 정수를 정확하게 표현할 수 있는 범위가 2의 53승 빼기 1까지이고, 이것이 Number.MAX_SAFE_INTEGER입니다. 반면 Java의 long은 64비트 정수 전체를 그대로 쓰기 때문에, Snowflake처럼 타임스탬프와 노드 번호, 시퀀스를 비트로 조합한 64비트 ID는 이 안전 범위를 쉽게 넘습니다. 서버가 이런 값을 JSON 숫자로 내려주면 브라우저가 파싱하는 순간 가장 가까운 표현 가능한 값으로 반올림되어 끝자리가 바뀌고, 그 값으로 다시 조회하면 존재하지 않는 리소스가 되어 404가 나는 식의 문제가 생깁니다. 서버 로그와 DB에서는 값이 정상이라 원인을 찾기 어려운 게 특징입니다. 해결 방법은 응답 경계에서 ID를 문자열로 직렬화하는 것입니다. 클라이언트에 BigInt 파싱을 요구할 수도 있지만, ID를 사용하는 모든 클라이언트가 규약을 지켜야 하므로 서버 한 곳에서 막는 편이 안전합니다. 같은 맥락에서 부동소수점은 0.1 같은 값도 정확히 표현하지 못하기 때문에, 금액 계산은 double 대신 BigDecimal이나 원 단위 정수를 사용해야 합니다.
